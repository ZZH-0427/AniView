### UI-001 — Engineering workload in normal product UI

- **ID:** UI-001
- **Priority:** P1
- **Surface:** Video conversion estimate; GIF creation limit error.
- **Viewport:** Global; particularly 360/390.
- **Problem:** Normal mode shows `Frame-pixel workload`, e.g.
  `5.76 MP / 15.36 MP`. Creator's rejection adds
  `(15,360,000 frame-pixels maximum)` to an otherwise useful instruction.
- **User impact:** A developer budget is presented as a user setting. At 360 px
  it wraps into several lines and adds scan/scroll cost without explaining a
  useful choice.
- **Evidence:** [Video estimate, 360](v0.2-ui-ux-audit/ui-001-workload-360.png);
  [Creator rejection, 390](v0.2-ui-ux-audit/ui-001-creator-limit-390.png).
- **Recommended fix:** Normal summary: duration, output size and estimated
  frames; errors: reduce clip length/frame rate/output size, or fewer/smaller
  images. Retain the exact budget in existing debug JSON. Keep useful user limits
  such as 150 frames or 30 seconds when relevant.
- **Scope:** Presentation/copy only. Remove no checks and change no arithmetic.
- **Regression risk:** LOW; text/layout assertions and debug retention.

### UI-002 — Input errors are remote from their controls

- **ID:** UI-002
- **Priority:** P1
- **Surface:** Video source admission, Trim, Output/preflight.
- **Viewport:** Global; most disruptive at 390/360.
- **Problem:** Start 6 / End 5 is rejected in Estimated result, after Output.
  Neither input has `aria-invalid` or `aria-describedby`. An unsupported source
  shows Prepare again near the picker but its explanation is below the disabled
  form and Convert action.
- **User impact:** Users editing Trim may see no reason for the disabled Convert
  button. After selecting a bad source, the first phone screen suggests retrying
  the same file without explaining why it failed. Assistive technology has no
  field-to-error association.
- **Evidence:** [Trim controls, 360](v0.2-ui-ux-audit/ui-002-trim-fields-360.png);
  [separate message, 360](v0.2-ui-ux-audit/ui-002-trim-message-360.png);
  [unsupported source first screen, 360](v0.2-ui-ux-audit/ui-002-source-error-360.png).
  At 390 the trim fields are at y≈849 and the error at y≈1323. The actual
  unsupported-source follow-up at 360 placed the picker at y≈141 and error at
  y≈1338. Positions are document CSS pixels.
- **Recommended fix:** Show source preparation/failure beside the picker; place
  trim failures in Trim, and size/frame-budget failures near Output/summary.
  Use the existing `Preflight.issue` discriminator, stable error IDs,
  `aria-describedby` and appropriate `aria-invalid`. Prefer one relevant live
  message over duplicate alerts. Give the end-time boundary when helpful.
- **Scope:** UI placement, derived validation presentation and accessibility
  attributes. Existing classifications, source handling and all guards remain.
- **Regression risk:** LOW–MEDIUM; check stale errors, phase changes, valid
  correction, disabled fieldsets, duplicate announcements and source replacement.

### UI-003 — Single-source Creator has an unexplained disabled action

- **ID:** UI-003
- **Priority:** P1
- **Surface:** Create GIF.
- **Viewport:** All five widths.
- **Problem:** With one valid image, the page shows `1 / 200 images`, settings
  and disabled Generate GIF, without stating that at least two are required.
- **User impact:** The limit display looks satisfied, but the next action seems
  unavailable for an unexplained reason.
- **Evidence:** [One source, 390](v0.2-ui-ux-audit/ui-003-one-image-390.png).
- **Recommended fix:** Add a short helper near the list/action: “Add at least
  2 static images to create a GIF.” Associate it with the disabled-action context;
  stop showing it once the existing requirement is met.
- **Scope:** Copy and derived UI only; do not permit a one-frame job or alter
  CreationSession ownership/admission policy.
- **Regression risk:** LOW; verify zero/one/two sources and admission notices.

### UI-004 — Preview return loses result position and focus

- **ID:** UI-004
- **Priority:** P1
- **Surface:** Creator, animation conversion, MP4 Preview, video conversion.
- **Viewport:** Global; highest friction on 390/360.
- **Problem:** Preview → Close/Back remounts setup at document top, with focus on
  BODY. The result remains in memory but is offscreen. This was confirmed with
  actual CDP pointer events, not inferred only from programmatic DOM clicks.
- **User impact:** Preview → Download requires finding the same result again.
  Keyboard navigation starts over at Home/Back rather than the result action.
- **Evidence:** [Result before Preview, 390](v0.2-ui-ux-audit/ui-004-result-before-390.png);
  [after closing Preview, 390](v0.2-ui-ux-audit/ui-004-return-after-390.png).
  After pointer Close: scrollY=0, result top≈1606, Preview≈1812, Download≈1868;
  the next Tab focuses `video-conversion-back`. All four Preview return paths
  were observed with BODY focus. No Blob/session loss was observed.
- **Recommended fix:** Restore the result/opener context after existing Viewer
  teardown joins: focus the new Preview button or result heading and bring that
  region into view. Do so only on Preview return, not every settings edit/job.
  Respect reduced motion; introduce no media persistence/router.
- **Scope:** Workspace-level UI scroll/focus behavior. No Session, Player,
  Decoder, pipeline or resource-ownership changes.
- **Regression risk:** MEDIUM; asynchronous teardown, lazy native preview,
  remounts, absent/stale results, Home exit and keyboard focus need targeted checks.

### Optional before v0.2

#### UI-005 — Home task descriptions lag V0.2

- **ID:** UI-005
- **Priority:** P2
- **Surface:** Home.
- **Viewport:** Global.
- **Problem:** “Local Animated Media Viewer” and the hero describe viewing only;
  Convert video does not state its animation destinations. Phone image/ZIP
  labels are Chinese while the surrounding product copy is English.
- **User impact:** First-time discovery is less direct; buttons themselves still
  work and lead to clear pages. This is not a broken entry flow.
- **Evidence:** Home screenshots/DOM at all widths in the evidence coverage;
  `Home.tsx`, `ImageInput.tsx`, `ArchiveInput.tsx`.
- **Recommended fix:** Short task descriptions for viewing, static images → GIF,
  and video → GIF/WebP/APNG. Make a deliberate product-language choice; do not
  confuse native OS picker language with AniView's own hard-coded labels.
- **Scope:** Copy; small local spacing if needed. No Home redesign/i18n framework.
- **Regression risk:** LOW; phone wrapping and accessible names.

#### UI-006 — Result units, order and action emphasis vary

- **ID:** UI-006
- **Priority:** P2
- **Surface:** All generated results.
- **Viewport:** Global; 360 for wrapped Download Animated WebP.
- **Problem:** Creator uses KiB and per-frame duration; converters use raw byte
  counts and total duration. Frames/duration/playback appear in different orders.
  Old Convert/Generate remains the strongest visual action after success;
  Creator Preview/Download are flatter than converter buttons.
- **User impact:** Extra scanning across tools, without blocking Preview or
  Download. Wrapped result buttons remain readable and at least 44 px high.
- **Evidence:** Result text/geometry in evidence; each target actually generated.
- **Recommended fix:** Consistent readable file-size units and metadata order.
  Consider Download as the completion primary action, Preview secondary, and
  consistent small-screen stacking. Do not add another result route.
- **Scope:** Result presentation/CSS/copy; optional derived one-cycle duration
  for Creator, with no re-encode or new session state.
- **Regression risk:** LOW; long names, native downloads and preview controls.

#### UI-007 — Output labels could explain units more directly

- **ID:** UI-007
- **Priority:** P2
- **Surface:** Video Output; MP4 target naming.
- **Viewport:** Global.
- **Problem:** `FPS`, bare `360/480/720`, and `Original` assume context. Original
  may subsequently fail the existing 720 cap; orientation/display dimensions
  mean it is not a pixel-fidelity guarantee. MP4's H.264 qualifier is secondary.
- **User impact:** Some experimentation is needed, but immediate limits and
  the no-upscaling/aspect-ratio note already prevent a misleading successful job.
- **Evidence:** Output DOM; actual portrait Original rejection; format labels.
- **Recommended fix:** “Frame rate (fps)”, size in px, and a short source-size/
  720/no-upscale explanation. Use MP4 (H.264) where format context is needed.
- **Scope:** Labels/helper copy only. Native select versus radio is a justified
  difference, not a reason to introduce a shared selector or custom FPS.
- **Regression risk:** LOW; preserve values/options and accessible labels.

#### UI-008 — Some error copy remains specialist or lacks a next step

- **ID:** UI-008
- **Priority:** P2
- **Surface:** Source/encoder compatibility, timeline and resource errors.
- **Viewport:** Global.
- **Problem:** “opaque VP9”, “8-bit SDR”, “timeline structure”, “GIF encoding
  worker” and some generic decode/limit errors need plainer wording or a useful
  action. These are source-reviewed failure branches, not all freshly induced.
- **User impact:** Recovery guidance is uneven; stable internal error codes are
  nevertheless not displayed as ordinary error headings.
- **Evidence:** Six exact copy/preflight catalogs in evidence.json; inventory below.
- **Recommended fix:** What happened + smallest useful next step. Explain HDR/
  transparency in ordinary terms where necessary; retain accurate capability
  conditions, and avoid suggesting HTTPS alone fixes a missing browser API.
- **Scope:** Existing error-message functions only; no error-model/codec change.
- **Regression risk:** LOW; expected error-text assertions.

#### UI-009 — Video setup can be denser without a sticky action

- **ID:** UI-009
- **Priority:** P2
- **Surface:** Video source/summary layout.
- **Viewport:** All; especially 360 and portrait.
- **Problem:** At 360, landscape setup is 1859 px tall with Convert at y≈1716;
  portrait setup is 2023 px with Convert at y≈1880. At 1440 the representative
  setup is still 1621 px. Source metadata, notes and a standalone estimate add
  height. This is reachable scrolling, not a hidden action.
- **User impact:** Longer setup scan. Last output settings remain reasonably
  close to Convert, so a sticky Convert is **not a mandatory remedy**.
- **Evidence:** Video form geometry in evidence; landscape/portrait snapshots.
- **Recommended fix:** First remove UI-001's metric, compress metadata/summary
  and shorten redundant notes. Re-measure before considering any sticky bar.
  Keep native preview controls and readable input heights.
- **Scope:** Optional local spacing/summary layout. No two-pane redesign required.
- **Regression risk:** LOW–MEDIUM; portrait controls, keyboard viewport and 768.

#### UI-010 — Full Creator filenames are difficult to inspect on touch

- **ID:** UI-010
- **Priority:** P2
- **Surface:** Creator source list.
- **Viewport:** 390/360.
- **Problem:** Filename ellipsis correctly preserves the three row controls,
  but the full name is mainly in `title`/accessible row text. Hover is unreliable
  for touch; similar long prefixes are hard to distinguish visually.
- **User impact:** Secondary identification friction; order, remove and duplicate
  source behavior remain usable. It does not justify mandatory thumbnails.
- **Evidence:** Long-name single/three-source snapshots and source row markup.
- **Recommended fix:** Optional small, explicit way to expand/view the full name.
- **Scope:** Local disclosure only; no thumbnail cache/media decode.
- **Regression risk:** LOW–MEDIUM; touch target collisions and bounded list height.

## Responsive, visual and accessibility conclusions

- **390:** Required Home, Viewer, Creator, animation conversion/result, MP4
  result, video conversion/result, ZIP and error snapshots captured. No overlap
  or horizontal scroll. Video's displaced errors and Preview return are P1.
- **360:** Inputs/format/FPS/size selectors wrap cleanly into a single column;
  they do not form the hypothetical broken FPS grid. Native inputs/selects are
  48 px high. Main actions, menus and reorder/remove are at least 44 px; Creator
  checkbox has a 44 px clickable label. Native video internals remain browser UI.
- **Portrait preview:** Representative 390 preview is about 228×405; 360 about
  216×384. It is capped near 48% of viewport height, not a full-screen preview
  that hides all controls. No reason to replace native controls.
- **768:** Cards, radios, metadata and native video fit; no ignored breakpoint
  failure. **1280/1440:** Bounded content widths are sensible. Video can be less
  tall (UI-009); spare desktop space alone does not justify a redesign.
- **Hierarchy:** Viewer media remains dominant. Shared light backgrounds, blue
  actions, grey metadata, rounded cards and one stroke icon family are coherent.
  Creator is more compact; this is P2 polish, not three incompatible applications.
- **Keyboard:** Actual Tab showed a visible blue 3 px focus outline. More End
  focused Remove from list; Escape closed the menu and restored More. Native
  controls/labelled selectors were reachable. No modal/menu/Preview trap was
  observed. Full screen is capability-dependent; this is not new Android native
  fullscreen certification. Result-context restoration is UI-004.
- **Labels/disabled:** Icon controls have names; targets use native checked/
  disabled state plus “Already …”, not color alone. Start/End have visible labels
  but lack invalid/error linkage (UI-002). The one-source state needs UI-003.
- **Contrast:** Normal text, helper text, blue focus and red alerts had no obvious
  contrast problem in sampled views. Disabled controls are deliberately subdued.
  No formal WCAG or screen-reader certification is claimed.
- **Reduced motion:** Emulated reduce preference matched; no animated UI elements
  were found in the checked view. Media animation is the product's content, not
  decorative UI motion; do not disable it as a cosmetic change.
- **Loading:** Lazy entry fallbacks have visible status text. Source preparation
  should be shown near its picker (UI-002). No need for a new loading framework.
- **Unsupported browser:** Error mappings are feature-specific, with Home and
  non-video entry points kept separate. This is source-reviewed; missing
  WebCodecs was not simulated in this capable audit browser.
- **Privacy/debug:** Normal snapshots have no diagnostic panels, Worker counts,
  RGBA, PAR fallback, heartbeat or codec configuration. UI-001 is the specific
  engineering metric leak. Debug details and nested JSON start closed. No normal
  navigation links to the engineering harness were found; that is narrower than
  claiming experimental code can never be reached by a manually supplied URL.
- **Navigation/reload:** Navigation remains in-memory React state. Refresh loses
  these sessions and returns Home; browser history is not an internal router.
  This established policy is not a new blocker or a request for persistence.
  UI-004 concerns return within a live product flow, not reload recovery.
