## 3. Current archive baseline

ZIP remains `@zip.js/zip.js@2.23.0`, including accepted ZipCrypto/AES128/192/256.
`ArchiveInput → ArchiveSession → archive.worker/ArchiveEngine → ZipReader →
ArchiveEntryVirtualFile → MediaSession → Viewer` is frozen. Session owns one
private recent successful password, serial extraction/generation, one current
verified Blob, and Worker lifecycle. Engine owns one Reader and entry metadata.
The keyed UI access gate precedes Viewer for selected encrypted entries.
Converter borrows the same VirtualFile/session; source replacement awaits Viewer
cleanup before closing the old archive. There is sequential file navigation and
an archive summary, not an existing general-purpose archive file-list browser.

Limits: 512 MiB encoded archive, 16 MiB directory/read allocation, 10,000 entries,
64 MiB actual entry output, 2 GiB declared total, declared ratio 1000, path length
1024 and cumulative paths 2 Mi characters; MediaSession 1000 files. Existing
request/close bounds are 30 s / 2 s. These are ZIP policy, not transferable RAR/7z
safety guarantees. VirtualFile.read is asynchronous; WORKERFS consumes File/Blob,
not an arbitrary async VirtualFile.read callback.

## 7. Security and maintenance

Checked upstream: 7-Zip 26.05, libarchive 3.8.11. sevenzip-wasm 26.5.0 pins the
current 7-Zip tag/submodule and supplies source patch/build scripts; small maintainer
footprint remains a supply-chain consideration. 7z-wasm's 24.09 omits subsequent
upstream fixes. Do not extrapolate Windows Mark-of-the-Web vulnerabilities into a
browser escape: host filesystem behaviors differ, but obsolete parser builds are
still poor new dependencies.

libarchive-wasm/archive-wasm ship 3.7.7; libarchive.js ships 3.7.2. The upstream
[GHSA-6vpf-5947-22g5](https://github.com/libarchive/libarchive/security/advisories/GHSA-6vpf-5947-22g5)
lists 3.6.0–3.7.9 affected and 3.8.0+ patched; no backport is evidenced in these
builds. It is a parser memory-safety risk, not a tested browser exploit. Other
linked crypto/codec versions also need review before a fresh custom build.
node-unrar-js lacks verified exact native release provenance. @unrar-browser/core
vendors UnRAR 7.10; later [RARLAB changes](https://www.rarlab.com/rarnew.htm) include
security fixes, some specific to recovery/disk behavior and not automatically
applicable to a DLL-style browser reader. Do not label an old engine current.

## 8. RAR support

sevenzip 26.5.0: RAR4 and RAR5 content hashes T; RAR4/RAR5 solid T (including later
RAR4 solid d.txt in encrypted-data and encrypted-header fixtures); password data and encrypted filenames
T for both RAR4 and RAR5. Multi-volume is technically T with all supplied parts,
but recommended OUT OF SCOPE initially. No SFX support commitment.
libarchive-wasm passes ordinary RAR4/RAR5/RAR5 solid. Current libarchive source
explicitly rejects RAR4 solid. Encrypted RAR4 may surface a decode error such as
Invalid PPMd sequence; RAR5 encrypted data reports unsupported. These wrappers
must not call every such failure a bad password.

## 9. 7z support

sevenzip normal/solid and password/header encryption T. Nine codec/filter probes
T. libarchive-wasm passes ASCII entry probes, but this build replaces Chinese
pathnames with `**` and cannot retrieve the original later Unicode path; normal
ASCII extraction succeeds. This is a measured wrapper/build behavior, not proof
that libarchive universally cannot handle Unicode. Libarchive's source rejects
7z AES content/header decryption even when a passphrase API exists.

## 10. Input and filesystem model

sevenzip's existing WORKERFS mounts immutable Blob/File input. FileReaderSync
reads are copied in bounded chunks to decoder buffers; no initial whole archive
ArrayBuffer is required. Maximum observed read chunk: 1 MiB. It is not a native
arbitrary async read callback, HTTP range backend or proof of zero native copies.
MEMFS input instead materializes an ArrayBuffer and a separate JS filesystem
buffer; do not mistakenly count this buffer as an archive-sized WASM allocation.
The output path still uses MEMFS and readFile unless a bounded stream/device is
adapted. Libarchive-wasm explicitly materializes and malloc/copies the entire input
into linear memory. No candidate needs a server upload.

## 11. Memory model and measured scaling

Small source: 1,341 bytes. Medium: 6,292,029-byte solid 7z, three 2 MiB entries,
4 MiB dictionary. Controlled larger: 25,165,995-byte non-solid COPY 7z, three
8 MiB entries. Only original synthetic content was generated.

sevenzip WORKERFS high-water: **17,039,360 bytes** linear memory at all three
sizes. Large selected 8 MiB output has MEMFS capacity **8,736,646 bytes**, plus
the 8 MiB readFile result. Input mount does not grow that linear heap with archive
size. This does not measure output JS/native memory or guarantee all dictionaries
fit. libarchive-wasm: initial 17,104,896, large-input open 30,605,312, extraction
high-water **36,765,696 bytes**, in addition to full JS input/output objects.

Conservative ownership model: source backing B + allocated WASM H (dictionary is
already inside H, do not double-count it) + temporary read R + output filesystem
capacity C(O) + returned output O + future Blob/transfer ownership. MEMFS input can
add an archive-sized JS copy; libarchive adds B inside H plus its JS full-buffer
step. GC and Blob backing sharing make exact simultaneous peaks unobservable.
OS/native/compiler/GPU/cache memory is not measured. A 512 MiB ZIP allowance is
therefore not appropriate evidence for a RAR/7z cap.

## 12. Cancellation

These synchronous engines cannot process a queued Worker cancel message during
decode. The tested reliable cancellation boundary is terminating the dedicated
Worker, then creating a fresh one and reopening the source. This discards the
WASM heap and pending task, but does not claim immediate physical OS memory return.
No cooperative AbortSignal API was found in the chosen CLI interface. Five
open/extract/close cycles pass; ordinary close does not shrink a WASM high-water.

## 13. Worker and lifecycle

Main thread handles coordination, Blob messages and numeric summaries only.
Decode/crypto/FS work runs in a dedicated Worker. Desktop run: 39 created/39
terminated, active 0, peak 1, including comparisons and one cancel→reopen.
sevenzip had 29 successful cases plus one cancellation; libarchive comparison
had five successful cases and four failures retained in the report, not hidden.
Main heartbeat max 17.7 ms in that run, not proof of all-device responsiveness.
First fresh-profile small factory readiness was 13 ms; five subsequent instances
were 10.3–12.8 ms. This timing includes local asset fetch/factory initialization,
not a pure compiler benchmark or phone/network startup guarantee. Large COPY
open/list took 26.5 ms; first/later 8 MiB extraction+hash took 69.5/71.6 ms. The
later separate RAR4 solid and multi-volume probes also passed; they are not folded
into the original 39-Worker counter snapshot.
The libarchive comparison's first factory readiness was 9.6 ms and later instances
8.3–10.0 ms; large-input open/list was 39 ms. These are the same local-fetch timing
scope, not evidence that a stale binary is safer because it initializes quickly.
Prefer one Worker per extended archive session; terminate on close, cancel or
hard failure. Reconstruct it only for that source, never a global shared heap.

## 17. Password model

7z/RAR encrypted headers require an **archive-opening** access state before
enumeration, distinct from ZIP's selected-entry gate. Reuse the present labeled
password form with explicit archive-level help copy, not its ZIP-entry wording.
Keep the ZIP state machine intact. Extended session owns pending opening input
and one latest fully verified body credential; header decryption alone must not
silently promote a candidate as a fully validated data password. Passwords stay
local/nonpersistent/nonlogged; CLI argument arrays remain transient private
transport, never diagnostics. Prefer a structured native API over `-p...` argv.
Current experiment uses public fixture secrets only. Generic exit code 2/stderr
does not reliably separate password, corruption and unsupported errors.

## 18. Solid archive cost

Metadata-only listing does not publish entries' file contents, but can decode a
compressed/encrypted metadata header. Selecting a later solid entry can require
decoding all preceding bytes in its block. In the 6 MiB solid test, first entry
read 4,195,510 source bytes versus later entry **7,341,629**, including rereads;
max chunk 1 MiB. Only 2 MiB selected output was written each time. Counts are
source I/O, not a claim to directly measure every decoded byte or dictionary step.
Selection is lazy in *retention*, not guaranteed random-access decode cost. Each
CLI command reopens/scans the source despite reusing one WASM instance; do not
promise the same Reader semantics as ZIP or cache a whole solid block indefinitely.

## 19. Multi-volume and SFX

Two-volume 7z and eight-volume RAR5 pass selected-output hashes when all files are
mounted. Missing next volume returns code 2 and no published output. This engine
capability does not supply AniView's volume selection, pairing, limits or UX.
Initial product recommendation: defer .rar+.r00/.partN.rar/.7z.001 sets, SFX,
recovery records, automatic nested archive browsing and non-whitelisted formats.
ZIP entries containing archives remain ordinary files; do not recursively open.

## 20. Path and metadata safety

Normalize minimal metadata: id, path, uncompressed size, optional packed size,
directory/regular/link/special classification, encryption state, method/block and
dictionary information when actually available. Packed size can be block-shared
or absent; unknown must not become zero for ratio division. Reject ../, absolute,
drive/UNC, NUL/control/bidi-dangerous names and unsafe lengths; skip links/special
files as media, preserve directory semantics. Do not execute extracted content.
Force native format selection only after binary whitelist detection. Signatures:
RAR4 `52 61 72 21 1A 07 00`; RAR5 `52 61 72 21 1A 07 01 00`;
7z `37 7A BC AF 27 1C`. No product detector/picker was changed.

## 21. Limits and unresolved hard boundary

Measured pre-write guard: rejecting an 8 MiB output against a 1 KiB cap yields
code 2, no result/hash and **zero retained output capacity** in the experiment.
That does not cap earlier decoder dictionaries or metadata/header allocation.
The prebuilt sevenzip binary defines its own wasm32 memory, initial 17,039,360,
max **2,147,483,648** bytes; it does not import a memory whose maximum AniView can
simply replace. No proven factory option reduces that compiled maximum.
CLI metadata exposes human-readable methods such as `LZMA2:22` (the fixture's
4 MiB dictionary) and `v6:m5:128K` for a tested RAR5 entry. This is not a typed,
complete memory requirement for arbitrary coder graphs, nor a pre-header-allocation
guard. Solid/shared packed sizes likewise cannot supply a universal ratio bound.
`-smemx` is present upstream, but it is not demonstrated as a universal 7z header,
method/dictionary and whole-engine hard budget. A JS grow hook used for observation
is not a security boundary against every internal WASM allocation/grow path.

Consequently **no numeric production RAR/7z limit is approved** from these tests.
The supported experiment envelope is only the explicit inputs/outputs above.
Before GO: prove bounded memory including hostile compressed headers, dictionary
preflight/allocator failure, selected actual-output cap, cumulative solid work,
entry/path counts, metadata budget and external deadline. Do not reuse 512 MiB,
10,000 entries or a 2 GiB heap maximum as safe phone settings. Choose any product
numbers only after bounded-build desktop and Android evidence.

## 23. Integration option A — backend under ArchiveSession

Introduce a generic ArchiveBackend inside the existing ZIP session. Benefit:
common ownership/cache/controller. Cost: reopens the accepted ZIP password,
metadata assumptions, cancellation and Reader semantics for format-specific
differences. High churn/regression risk; not recommended for the first addition.

## 24. Option B — completely parallel product workflow

Keep ZIP unchanged and add an extended session plus separate UI/source workflow.
Low direct ZIP parser risk, but duplicate navigation, source replacement, prompt,
conversion/Back and cleanup logic. Increases long-term test/maintenance burden.

## 25. Option C — shared UI-facing source contract

Keep the existing ZIP session implementation. Add one separate Rar7zArchiveSession
with a dedicated extended Worker, exposed through a small UI-facing archive source
contract. Existing ZIP can conform structurally or through a thin UI adapter.
VirtualFiles converge before MediaSession/Viewer; no codec/player branch by archive.

## 26. Recommended integration architecture

**Option C**, conditional on the safety/licensing spike. Factory chooses binary
kind → existing ZIP session or separate extended session. Narrow contract: identity,
name, files, normalized entry lookup, ensure/unlock/release, close and nonsecret
metrics. Keep format labels outside the ZIP class if that avoids adding runtime
members. Entry Gate depends on the narrow access contract instead of a nominal
concrete class. New archive-opening password orchestration surrounds enumeration;
it must not retrofit that state into the existing ZIP entry gate.

Estimate only: about 8–10 existing UI/source/type/notice files with localized changes,
8–10 new extended backend/source/manifest files, plus tests. Exact code size remains
unknown until the structured/safe backend API is proven. No refactor is performed.

## 27. Backend recommendation

Production backend: **NONE approved yet**. Leading spike reference:
sevenzip-wasm 26.5.0 / upstream 7-Zip 26.05. A source-reproducible bounded build
and structured/bounded output interface may be needed; do not silently ship a
patched anonymous binary or claim the npm package already supplies these guarantees.
One engine for both formats is preferable to adding a second stale UnRAR parser
with extra payload/ownership/test surface. A 7z-only product whitelist does **not**
remove unRAR terms from a binary that still contains that decoder.
