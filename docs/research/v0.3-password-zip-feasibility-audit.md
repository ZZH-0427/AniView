# M10B1 — Password-protected ZIP feasibility and architecture audit

Date: 2026-11-04. **COMPLETE — FEASIBLE. M10B2 READY.**
Read-only audit of product baseline `e57890b` (M10A2 closed), on
`feat/v0.3-password-zip`. No product code, dependency, Worker, test baseline,
historical milestone document, workflow or production artifact was changed.

## 1. Decision and scope

Keep **@zip.js/zip.js 2.23.0**. It already implements the required encrypted-entry
read path; no custom cryptography, new dependency or upgrade is needed.
Recommend **Option A: ArchiveSession owns one latest successful password**, with
a UI access gate before mounting the selected encrypted entry's Viewer. Pass
credentials per `getData` call; keep the existing Reader/entry identities alive.
Core implementation and new Android product acceptance belong to M10B2, not here.

Support planned: Traditional/PKWARE ZipCrypto, WinZIP AES-128/192/256, mixed public
and encrypted entries, per-entry lazy unlock, explicit retry, session-only reuse.
Exclude PKWARE strong/proprietary encryption, encrypted central directories,
password persistence/recovery/guessing, archive writing, RAR/7z containers, a new
archive file-list feature and extract-all. 7-Zip is a fixture producer only.

## 3. Encryption support and metadata

`lib/core/zip-reader.js:993–1058` chooses ZipCrypto when an entry is encrypted
without an AES extra field, rejects strong-encryption bit 6, validates AES strength
1..3 and obtains the underlying compression method from the AES extra field.
`aes-crypto-stream.js:52–58` maps strengths to keys 16/24/32 bytes, salts 8/12/16,
a two-byte password verifier and a ten-byte authentication tag.

| Variant | Read support | Evidence |
| --- | --- | --- |
| Traditional ZipCrypto | YES | source + own fixture + independently produced 7-Zip ZIP + real production Worker |
| WinZIP AES-128 | YES, strength 1 | same four evidence layers |
| WinZIP AES-192 | YES, strength 2 | same four evidence layers |
| WinZIP AES-256 | YES, strength 3 | same four evidence layers |
| PKWARE strong encryption | NO | flag-bit fixture → ERR_UNSUPPORTED_ENCRYPTION |
| AES strength outside 1..3 | NO | altered local/central AES strength → ERR_UNSUPPORTED_ENCRYPTION |
| Unknown compression/wrapper | not a supported encryption variant | altered method → ERR_UNSUPPORTED_COMPRESSION; do not call it a wrong password |
| Encrypted central directory | no built-in decryption | ERR_ENCRYPTED_CENTRAL_DIRECTORY; an external callback is possible but out of scope |
| Other proprietary/nonstandard schemes | excluded | an unrecognizable/malformed header can look corrupt or fail verification; universal scheme detection is not promised |

Encryption is **per entry**, not an archive-wide credential. Standard ZipCrypto
and WinZIP AES leave filenames and central-directory size/method metadata visible.
`EntryMetaData`/FileEntry expose encrypted, zipCrypto, rawBitFlag, compressionMethod
and extraFieldAES.strength/vendorVersion. The AES parser replaces method 99 with
its actual STORE/DEFLATE method. Current AniView retains encrypted + underlying
compressionMethod, sizes and access state; it does **not** retain AES strength or
encryption kind. Strong encryption/symlinks/split entries are currently reduced
to an unsupported method before policy validation.

## 4. Exact password APIs — core versus ZipFS

Core APIs present in 2.23.0:

```ts
new ZipReader(reader, { password, rawPassword, /* other options */ })
entry.getData(writer, { password, rawPassword, signal,
  checkCrc32: true, checkAuthenticationCode: true })
entry.getData(writer, { password, checkPasswordOnly: true })
```

`index.d.ts:1644` makes constructor options extend ZipReaderOptions; password is
declared around 1984, rawPassword/signal around 2014–2027. Per-call values override
Reader values (`zip-reader.js:1971`). An empty password/raw array is normalized
to absent by the core Reader; preserve nonempty whitespace and Unicode without
trimming. `checkPasswordOnly` is only a short verifier check, never sufficient
for promoting a password or publishing media.

**Important exact-version finding:** `passwords`, `requestPassword` and a
successful-password cache really DO exist in this version, in
`PasswordCandidatesOptions` (`index.d.ts:4636–4709`) for the **ZipFS import/export/
ZipFileEntry** layer. They are not core ZipReader options. A runtime experiment
passed them to core ZipReader: callback calls 0, read rejected ERR_ENCRYPTED.
Do not silently assume the filesystem convenience layer applies to AniView.
Its own documentation also warns that its ZipCrypto retry policy treats some
corruption as a wrong password. Adopting ZipFS would replace useful existing
bounded extraction/session logic and is not recommended.

The Reader and the same entry object survived wrong→correct calls and mixed
entries using different passwords in the audit. No reopen/re-enumeration needed.

## 5. Errors and authentication

The exports are stable **string constants**; the relevant ordinary errors have
name Error, message equal to a constant, and **no numeric/symbolic error.code**.
Some have outputSize; that is not an error category. Compare the imported constant
at the vendor adapter boundary, not a copied/localized human sentence. Current
archiveFailure already follows this pattern for password/unsupported errors.

| Exported constant | Actual message | Planned product interpretation |
| --- | --- | --- |
| ERR_ENCRYPTED | File contains encrypted entry | ARCHIVE_ENCRYPTED; request input |
| ERR_INVALID_PASSWORD | Invalid password | ARCHIVE_WRONG_PASSWORD; verifier rejected; permit explicit retry |
| ERR_INVALID_AUTHENTICATION_CODE | Invalid authentication code | ARCHIVE_CORRUPTED/integrity failure, not an automatic wrong-password claim |
| ERR_INVALID_CRC32 | Invalid CRC32 | corrupted for plain; ambiguous password-or-corruption for ZipCrypto |
| ERR_INVALID_COMPRESSED_DATA | Invalid compressed data | same ZipCrypto ambiguity; otherwise corrupt |
| ERR_INVALID_UNCOMPRESSED_SIZE | Invalid uncompressed size | same ZipCrypto ambiguity; otherwise corrupt, while preserving explicit AniView cap errors |
| ERR_UNSUPPORTED_ENCRYPTION | Encryption method not supported | proposed ARCHIVE_UNSUPPORTED_ENCRYPTION |
| ERR_ENCRYPTED_CENTRAL_DIRECTORY | Encrypted central directory is not supported | proposed ARCHIVE_UNSUPPORTED_ENCRYPTION, archive cannot list normally |
| ERR_UNSUPPORTED_COMPRESSION | Compression method not supported | existing ARCHIVE_UNSUPPORTED |
| ERR_EOCDR_NOT_FOUND | End of central directory not found | ARCHIVE_CORRUPTED for truncated ZIP |

No error should carry password, rawPassword, input value, candidate length/hash,
request options or a captured credential closure in UI/diagnostics data.
Vendor nested-worker serialization (`web-worker-base.js:238`) includes message,
stack, optional code/name/outputSize/cause; it does not invent a missing code.
AniView disables that nested pool and sends its own code-only ArchiveResponse,
with an aborted boolean for cancellation. Keep that narrow transport.

### Measured matrix

| Case | ZipCrypto | AES-128/192/256 |
| --- | --- | --- |
| No password | ERR_ENCRYPTED, no plaintext | ERR_ENCRYPTED, no plaintext |
| Chosen wrong password | ERR_INVALID_PASSWORD | ERR_INVALID_PASSWORD |
| Correct password | 114 exact expected bytes | 114 exact expected bytes each |
| Correct password + corrupted payload/tag | ERR_INVALID_CRC32 | ERR_INVALID_AUTHENTICATION_CODE |
| Correct password + corrupted salt/verifier | can fail password verification | observed ERR_INVALID_PASSWORD |
| Unsupported strong flag/strength | unsupported, never prompt as wrong | unsupported, never prompt as wrong |
| Truncation | structural failure | ERR_EOCDR_NOT_FOUND in tested sample |

Traditional ZipCrypto validates one byte (`zip-crypto-stream.js:43–57`): a wrong
password can pass with probability about 1/256 and fail only at inflate/CRC/size.
This is established by source and shipped documentation; no password search or
cracking experiment was performed. Correct-password corruption and these
false-accept cases cannot generally be distinguished. Plan a retryable
**ARCHIVE_PASSWORD_OR_CORRUPTED** state with honest wording, not a definite wrong
password or an endless automatic retry. Cache only after the complete read passes.

AES checks a two-byte verifier; a wrong password can very rarely pass it too.
Authentication is enabled by default (`aes-crypto-stream.js:65`), and explicitly
enabled by AniView. AE-1 can additionally use CRC; AE-2 intentionally has no
meaningful CRC, so authentication must never be disabled. A corrupted salt caused
ERR_INVALID_PASSWORD despite the known correct input. Therefore even a verifier
error is not mathematical proof that the user typed the wrong secret.

**Authentication is final, not a streaming trust guarantee.** A one-MiB stored
AES fixture with a changed authentication tag delivered 786432 bytes to the test
sink before failing. The sink abort removed all retained chunks (0 afterwards).
Never send partial plaintext to detection, Viewer, conversion or a Blob cache.
Use a fresh bounded writer for every attempt and publish only after getData plus
actual-size checks and stale checks succeed. This matches the existing engine.

## 6. Cancellation and resource behavior

`ZipReaderOptions.signal` is real. Source `codec-worker.js:116–125,233–237` passes
the signal into source/progress and final pipeTo paths; Reader checks it before
and after the pipeline. Pre-aborted, input-read abort and output-write abort all
rejected with AbortError and allowed the same Reader to retry successfully for a
one-MiB AES DEFLATE entry. Output-write abort had produced 262144 bytes; the sink
abort ran. Reader close is not a substitute for cancelling an active stream.

Cancellation is cooperative. Native PBKDF2 has no AbortSignal parameter and a
synchronous codec chunk cannot be interrupted mid-instruction. Shipped types
warn older engines may finish writing before rejecting. Preserve AniView's
per-request AbortController, joined operations, 30 s request bound, and 2 s
close-handshake fallback followed by Worker.terminate. A close/abort does not
promise immediate physical erasure of library/native allocations.

Actual frozen production Archive Worker in installed Edge: encrypted cancel →
aborted response → same-engine retry returned 1048576 bytes → normal close. Eleven
Workers created/terminated, active 0; no browser errors, external requests or
nested Worker assets. This is desktop feasibility, **not M10B2 Android acceptance**.

## 7. Current AniView flow and ownership

```text
ArchiveInput / archive drop
  → MediaApp → useMediaSource.openArchive/replace
  → lazy import ArchiveSession.open(File)
  → archive.worker.ts open
  → ArchiveEngine.open → BoundedArchiveReader + ZipReader.getEntriesGenerator
  → validated ArchiveEntryMetadata[] → ArchiveSession.files
  → ArchiveEntryVirtualFile → MediaSession item → selected Viewer
  → useViewerMedia → formats/open-media → binary detection / normal decoder
  → VirtualFile.read → ArchiveSession.extractEntry → Worker / Engine.getData
```

Real source anchors:

- `src/app/use-media-source.ts`: lazy archive import; replacement waits for Viewer
  transition cleanup, closes old archive; stores active session, aborts stale opens.
- `src/archive/archive-engine.ts`: owns the actual Reader + Entry objects **inside
  the archive Worker**, metadata validation, bounded extraction, integrity checks.
- `src/archive/archive-session.ts`: owns one Worker/transport, frozen metadata and
  VirtualFiles, current Blob/active request, generation, metrics and close gates.
  It does not currently own navigation or current MediaSession index.
- `src/media/media-session.ts`: current index, Next/Previous/remove/list references;
  input caps the visible media session at 1000 items, separately from 10000 ZIP entries.
- `src/app/MediaApp.tsx`: owns UI navigation and borrowed conversion source;
  conversion hides the source Viewer while keeping the archive session alive.
- `src/pages/Viewer/use-viewer-media.ts:126–136`: abort/open/decode cleanup plus
  `file.release()` is joined into transition.current; source replacement waits on it.

There is currently an archive summary and sequential Viewer navigation, **not a
ZIP entry-list picker**. The first media item is automatically selected. Therefore
an encrypted first selected entry may legitimately show its unlock UI after open;
do not unconditionally prompt because any sibling is encrypted, or add an entry
browser under this scope. Lock indication for the selected entry is useful; a
new per-row lock/list feature is optional future work, not an M10B2 requirement.

## 8. Lazy extraction, reads and plaintext lifetime

ArchiveEngine.open scans directory/metadata with **0 getData extractions**, also
measured on all eight external STORE/DEFLATE fixtures across four encryption
variants. Small ZIPs may have their
whole encoded bytes covered by the vendor's footer/directory read; this does not
mean their entries were decompressed/decrypted. No extract-all operation exists.

`ArchiveEntryVirtualFile.read(start,end)` obtains the session's materialized Blob,
then slices it to a **fresh** ArrayBuffer; arguments are [start,end), not a length.
Decryption/DEFLATE normally starts at the entry's beginning. It is not a random
access cipher service. Concurrent reads coalesce; range reads of the current entry
reuse its one Blob. A→B→A re-extracts A; no visited-entry/global plaintext cache.
releaseEntry drops current Blob and joins active cancellation; close drops lists,
cache and Worker. The borrowed VirtualFile depends on its archive staying alive.

Existing seam: extractEntry already accepts `{password?, signal?}`, and the Worker
command/Engine forward them. But the no-password guard is **before cache access**
and VirtualFile.read never passes a password. Pre-extracting once alone therefore
does not unlock later reads. M10B2 must resolve session credentials/cache at that
guard. Also, same-entry active coalescing currently ignores password identity:
a new submitted credential must abort/join the old attempt, not reuse its promise.

## 9. Current limits and encrypted safety

| Guard | Current value / enforcement |
| --- | --- |
| Encoded archive | 512 MiB before Worker/Reader |
| Central directory / individual Reader allocation | 16 MiB bounded reader range before vendor allocation |
| All ZIP entries | 10000 during enumeration, including hidden/directory entries |
| One entry plaintext | 64 MiB declared preflight and bounded actual sink |
| Total declared uncompressed | 2 GiB accumulated during enumeration; not an extract-all allowance |
| Declared uncompressed/compressed ratio | 1000:1 per entry before extraction |
| One normalized path | 1024 characters |
| Cumulative raw path lengths | 2 Mi characters |
| MediaSession items | 1000, separate existing UI list bound |
| Active plaintext entries | one current Blob and one serialized active extraction |
| Request / close fallback | 30 s / 2 s before hard Worker termination |

Source of truth: `archive-policy.ts`, `archive-engine.ts` boundedBlobWriter and
BoundedArchiveReader, `archive-session.ts`, `media-session.ts`. Do not raise them.
Declared sizes/method/CRC are readable but untrusted preflight data, never proof
of correct output. Actual sink rejects before retaining/copying an excess chunk;
final size must equal the declaration, CRC is checked where meaningful, AES auth
must pass. Correct-password and wrong-password attempts use identical limits.

The declared compressed size includes encryption overhead; the current ratio is
the existing declared container ratio, not a proof of the underlying DEFLATE
ratio. Forged metadata cannot guarantee low CPU/native allocation. Existing
actual output caps, chunk processing and Worker timeout remain necessary; do not
claim the 2 GiB declaration or password validation makes full extraction safe.
Metadata overflow/ratio/total guards precede password requests; blocked entries
must not become unlockable simply because a secret was supplied.

## 10. Security, privacy and logging

Current archive source has no console logging of request/options/password. Worker
errors are code-only. ArchiveSummary serializes numeric metrics, not entries or
requests. Runtime diagnostics contain numeric resource counters; MediaError uses
stable messages. Keep all candidate/UI state outside metrics, JSON, cause chains,
URL/query, storage, snapshots, analytics and network requests. Do not spread a
Session object or Worker command into diagnostics during M10B2.

Passwords and decrypted plaintext must enter local browser memory to do the job.
JavaScript strings, structured clones, Web Crypto and browser/native allocators
cannot be reliably actively zeroed by this app. The policy is prompt reference
removal and no persistence/logging, **not physical-memory secure wiping**. No
media/password upload API, persistent plaintext filesystem or global cache.

## 11. Options and chosen password policy

| Option | Benefits | Costs / lifecycle risks | Decision |
| --- | --- | --- | --- |
| A: Session credential + per-extract option | matches current password transport; same Reader; one owner; current cache/retry gates reused; small tests/diff | requires private credential state and pre-Viewer access gate | **RECOMMENDED** |
| B: async resolver/provider from a failed entry | abstracts credential source, could serve more UIs | pending resolver lifetime/cancellation; UI callback accidentally stored below UI; stale prompt/duplicate request complexity | unnecessary for one local UI; do not pass UI resolver into VirtualFile/Worker |
| C: recreate Reader with new password | constructor API works | no API necessity; rebuild metadata/entry identities, lose current cache/navigation, extra reads/Workers, harder close/retry | reject |

Use **one latest successful password**, private to each ArchiveSession. Same-secret
next entry tries it once automatically. Failed cached credential is dropped and
input requested; never loop. A new credential is promoted only after full
authenticated/size-checked extraction and current-generation validation. Public
entries do not replace it. With A=X/B=Y, successful B replaces X and returning to
A may prompt again. This small deterministic V0.3 scope is preferred to holding
multiple sensitive candidates; no per-entry password map, failed-candidate cache,
ZipFS candidate machinery or arbitrary unlimited list. Future expansion needs a
separate bounded/session-local design, not this first implementation.

## 12. Ownership proposal

| State | Owner | Lifetime | Cleared when |
| --- | --- | --- | --- |
| Typed/edited password, show flag | Archive password UI local state | selected entry's active unlock panel | success, Cancel, entry switch, archive replace/close, unmount |
| Submitted attempt | transient Session call / Worker operation | one joined extraction attempt | success/failure/abort/stale settlement; drop references |
| Latest successful password | private ArchiveSession field, no public snapshot | current archive only | rejected automatic candidate; new success replaces; close/terminate/Home/replace |
| Failed user input | UI only, never candidate cache | may remain editable while same panel shows inline error | edit/Cancel/entry change/success/close |
| Pending retry/entry | Session extraction generation + UI selection token/AbortController | one archive-ID + entry-ID + selection generation | switch, cancellation, close, replacement or completion |
| Authenticated plaintext Blob | existing Session current-entry cache | current materialized entry | release, new extraction, close/terminate |

No password goes in VirtualFile metadata. Session close must clear credential
references immediately before awaiting Worker shutdown; terminate does the same.
Cancel panel aborts/joins only pending work and leaves the archive usable.
Switch A→B cancels A and creates a new selection generation; late A success or
submission cannot cache credentials, open a Viewer or resurrect an old archive.

## 13. UI, language, navigation and conversion proposal

Use an **inline archive-flow access panel**, not a browser prompt, decoder dialog
or new modal. It includes associated password label/input, Show/Hide (type toggle),
Unlock, Cancel, inline error and existing Previous/Next navigation while locked.
On Cancel remain on a locked selected entry with an explicit Unlock trigger;
do not auto-prompt again or close the ZIP. Allow Next/Previous and Close archive.
Reuse `FileNavigation` from ViewerControls without altering playback internals.
Mount the Viewer only after complete entry availability; decoder sees plaintext.
Conversion continues borrowing the same entry. Keep session/password and selected
entry readiness across conversion→Back; existing plaintext may be re-materialized
after Viewer release using the session credential, never a credential on the file.

Use autocomplete="off", no username/login credential purpose, spellcheck=false,
autocapitalize=none, preserve paste/Unicode/whitespace; form submission must be
prevented from navigating or posting. This is a recommendation based on the
[HTML autofill standard](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#autofilling-form-controls:-the-autocomplete-attribute),
not a guarantee: user agents/users can override autocomplete preferences. Do not
mislabel an archive secret as current-password, new-password or one-time-code.
Focus input on open, Enter unlocks, Escape cancels when focus is within the panel,
aria-describedby associates errors, focus returns to the entry's Unlock trigger.
An inline panel needs no modal focus trap; use normal page scroll and small-screen
keyboard-safe layout. Show/Hide resets with the panel, no persistent preference.

M10B2 EN/ZH categories: required/enter/show/hide/unlock/cancel/unlocking/locked/retry,
verifier rejection with possible damaged header, ZipCrypto password-or-corruption,
unsupported encryption and integrity failure. Current 303 keys remain unchanged.

## 15. Bundle, assets, browsers and Pages

Existing package imports select WASM-flavored core; AES/ZipCrypto streams and an
inline zlib/AES WASM module are already present in the frozen 139317-byte archive
Worker. Inspectable markers include Invalid authentication code, Invalid password,
PBKDF2 and aes_hmac_new. The actual Worker successfully decrypted the fixtures
without new external assets. AES may initialize **existing embedded WASM**; this
does not mean it needs a new WASM file or no WASM work at all. JS AES/HMAC/PBKDF2
fallbacks exist; native subtle PBKDF2 is an optimization, not the only read path.

AniView sets useWebWorkers=false for zip.js because it owns a dedicated Worker.
No workerScripts override is configured. Native compression stream use follows
vendor capability selection; the bundled fallback covers missing native routes.
No new Worker asset, external WASM, cross-origin isolation, CSP relaxation or
runtime library should be necessary. New UI/state/error text has a small but
**not yet measured** M10B2 bundle cost. Do not claim zero product bytes before it
is built. Password UI must remain on the lazy archive path.

Required platform is the existing modern Worker/Blob/typed-array/streams browser
baseline. Edge and Quark are technically plausible; this audit does not operate
new Android password UI. Real keyboard, scrolling, AES latency, cancel and cleanup
need fresh M10B2 Edge/Quark acceptance. Preserve `/AniView/` Worker URLs via Vite,
existing CSP/Pages static hosting and local-only processing.

## 16. Risks and readiness

| Level | Risk | Required mitigation / gate |
| --- | --- | --- |
| LOW | labels/autocomplete/metadata/MIME-neutral source pipeline | EN/ZH/accessibility tests; no eager ZIP bundle; no new Viewer codec branch |
| MEDIUM | same-entry in-flight credential coalescing, cache guard ordering | abort/join replacement attempt; session authorization before VirtualFile reads |
| MEDIUM | different-secret archives | one latest credential, clear failed automatic value, explicit re-prompt, no endless candidate loop |
| HIGH | ZipCrypto ambiguity / AES damaged verifier | honest retryable error categories; never classify every failure as definitely wrong password |
| HIGH | plaintext produced before authentication | fresh bounded sink, no cache/decoder publication until full integrity/size/stale checks |
| HIGH | stale prompt/archive replacement/secret references | session + selection identity, immediate clearing, joined abort, no old submission resurrection |
| HIGH | native codec memory / delayed cooperative abort on Android | unchanged limits, serial jobs, request deadline + hard close fallback, fresh phone tests |
| HIGH | accidental credential logging/persistence | private fields, code-only errors, no snapshot/request spread, inspect network/log/storage tests |

No unresolved library/API blocker remains. ZipCrypto ambiguity is an intrinsic
format property handled by the recommended honest error state, not a reason to
upgrade or implement crypto. Physical secret wiping and encrypted-directory
support are not promised. If implementation contradicts observed Reader reuse,
guard preservation, cancellation cleanup or Android feasibility, stop for a
focused spike instead of silently changing limits/dependencies/architecture.
